# Proposed R3 SARIF acceptance contract

Status: design only, 2026-11-24. No existing `codeql-openwrt` SARIF importer or
fresh SARIF handoff is claimed. The consumer at
`32b0c2f9b2d2e73de2839ef4c106aa2fa2d91797` has CSV and typed JSON
handoffs for specific observations; its `corpus/lock.json` pins LuCI
`b2e0be4b46ec0fd43394c081fa7c50657af14011`, which is neither historical
parent/fix pair. See [MVP-1.md](../MVP-1.md) for the staged release gates.

An isolated **explicit-query format probe** for the experimental OpenVPN rule
has now produced one SARIF result on a copy of its vulnerable database: rule
`ucode/m4/openvpn-raw-metadata-command`, URI
`usr/share/rpcd/ucode/luci.openvpn.uc`, region starting at 71:115 and ending
at column 132 (SARIF's exclusive end for the source text ending at byte column
131). The artifact location has `uriBaseId: "%SRCROOT%"`; the rule descriptor's
`defaultConfiguration.level` is `warning` while the result omits its own
`level`. The validator must resolve that base ID through the pinned stage and
derive the effective level from the rule when no result-level override exists.
This is useful schema evidence, not a default-suite or Linux R3 pass.

## Purpose and owner

R3 needs a **new consumer-owned acceptance step** in `codeql-openwrt`. It
checks actual fresh CodeQL output from the released producer. It need not feed
the existing setBlockDetect policy adapter: that adapter consumes a different
CSV/typed contract and does not authenticate SARIF. The first consumer action
can be a fail-closed CI validator that prints a compact accepted result record
and preserves the original SARIF artifact. Decide separately whether policy
reports should ingest any future SARIF findings.

## Proposed inputs

1. One immutable acceptance manifest per scenario, prepared from source before
   the run. It names the producer release/pack digest and suite, CodeQL CLI
   version, full upstream source revision and Git path/blob, staged source
   digest, expected installed-style path and any build/install transform. It
   declares the exact selected and expected successful-file multisets,
   expected extraction errors (normally empty), expected rule ID and exact
   result tuples including URI, line/column range and multiplicity. Parent,
   fixed, positive and eligible near-miss are separate scenarios; no one LuCI
   corpus revision is falsely claimed to contain both historical versions.
2. A fresh run receipt generated by the Linux job, with producer and source
   SHAs, clean/dirty state, tool/pack/lock digests, source and stage hashes,
   command argv/exits, phase timing/memory, database and output identities,
   complete successful-file/error query rows, resolved suite rule IDs, SARIF
   SHA-256, and job/run identifier. Bind every path to a run-owned workspace.
   The receipt is evidence within the trusted CI job, not independent proof
   that arbitrary supplied JSON was executed.
3. The actual SARIF v2.1.0 bytes emitted by `codeql database analyze
   --format=sarifv2.1.0`, with CodeQL version pinned. The local CLI 2.27.4
   advertises that fixed format; `sarif-latest` is unsuitable as an unattended
   stable schema because the CLI may change it on upgrade. The job passes the
   same bytes to the acceptance step and retains them as an artifact.
4. A source map from staged URI to upstream repo/Git path and installed path,
   with explicit byte equality or a documented transformation and digest.
   Source staged at `/usr/share/rpcd/ucode/...` is not automatically proven to
   be the bytes in a package image.

## Fail-closed checks

- Reject malformed SARIF, absent/multiple unexpected runs, missing rule
  descriptors, duplicate or unexpected result tuples, unknown rule IDs,
  invalid/missing physical location or out-of-scope URI, unexpected severity
  or extra alerts. Compare exact result multiplicity, not only set membership.
- Check each source hash and map the SARIF artifact URI to an allowed staged
  file. Validate one-based start/end line and column against the independent
  manifest; translate the oracle's inclusive source-text end to the SARIF
  region's exclusive end where applicable. If CodeQL emits a range that
  differs from the predeclared oracle,
  inspect source and model before revising the manifest.
- Check the extracted successful-file multiset and complete error rows from
  the actual diagnostic queries. A SARIF file with no alerts is inconclusive
  when the expected file is absent, errored or excluded by routing.
- Require the resolved suite rule set and emitted SARIF descriptor set to
  match their separate source-first manifest lists exactly. The observed
  default suite resolves two diagnostic queries yet emits no SARIF
  descriptors, so these sets cannot be equated. The local consumer parser
  prototype enforces both checks and has nine passing focused tests at
  consumer commit `a6f4956`; those tests remain offline.
- Require the vulnerable historical target once, the actual patched target
  absent, a known-positive once and each eligible near miss absent. Also fail
  on unexplained additional results in the selected scenario. Treat unexpected
  disappearance of a previously accepted alert as a model/selection review
  event, not an automatic improvement.
- Compare the receipt's SARIF hash to the bytes consumed and check all
  commands exited 0. An interrupted command is a failure. The validator can
  detect inconsistent files and manifests but cannot cryptographically
  authenticate a fabricated receipt supplied outside the trusted CI job.

## First implementation sequence

1. Once the producer rule ID and output location are stable, run `database
   analyze` locally on the already source-verified parent/fix/control matrix
   to observe the actual CodeQL SARIF shape. Freeze the manifest from the
   independent source oracle; do not copy observed coordinates into expected
   fields without review.
2. Add a small consumer parser and offline rejection tests for malformed,
   missing, duplicate, extra, wrong URI/rule/range, wrong source hash, missing
   extraction and receipt/SARIF mismatch. These tests verify the parser only.
3. Add a fresh pinned Linux workflow that creates run-owned databases for the
   selected source matrix, runs the released suite, writes receipt and SARIF,
   calls the consumer on those exact bytes, and retains raw artifacts. Verify
   the job after a clean checkout. This closes R3 only if all producer and
   consumer gates pass.

Later incoming-change CI uses a separate current-corpus manifest and trigger.
The historical matrix stays as a regression suite and does not by itself scan
new upstream OpenWrt or LuCI commits.

The local parser currently checks consistency of the compact supplied packet.
Before R3, the trusted job must verify actual checkout/pack/suite hashes and
bind commands to its source root, database and output paths. Extend the
receipt with upstream Git blob/revision, source-to-stage/install mapping,
complete diagnostic rows and phase timing/memory. The parser's check of the
`%SRCROOT%` marker does not establish SARIF `originalUriBaseIds` or installed
package bytes. These are integration gates, not properties proved by an
offline receipt supplied to the parser.

A separate local **draft suite** probe at producer branch commit
`78590f24ab20a69eb1ac70258a00165f453d305d` changed only the direct
handler rule metadata to `@tags security` and `@precision medium`. CodeQL
2.27.4 resolved the default suite to that rule plus the two extraction
diagnostics. On copies of already extracted historical parent/fix databases,
default-suite SARIF analysis exited zero in 2.222/2.223 seconds and emitted
one OpenVPN parent result at 71:115–132 and zero fixed results. Both SARIF
runs had only the direct-handler rule descriptor, confirming why resolved
suite members and emitted descriptor identities need separate exact lists.
This was a macOS copied-database probe, not a fresh Linux extraction, release,
installed-byte proof or producer-to-consumer handoff. Earlier setup attempts
failed dependency readiness/preflight and are not passes.

A later local **fresh** handoff at integrated draft producer commit
`299731d8e22112cf88680b89ee08915ff531d273` and disposable consumer
commit `a6f4956507e2cd2078ba7c3ac7270c2e0c343cd6` used three separate
new databases for OpenVPN parent, fix and pinned LuCI `swconfig`. Source-first
manifests and the source-derived parent SARIF span were frozen before
extraction. Each diagnostic reported its exact selected file once and zero
errors; the resolved suite contained the direct handler rule and two
diagnostics. Actual suite SARIF bytes went to `tools/sarif_accept.py` in the
same local run. All 30 commands exited zero; the consumer accepted one parent
result at 71:115–132 and empty fix/near-miss results. Receipts serialize
decoded successful-file paths and resolved QL `@id` values, and bind exact
SARIF hashes. This demonstrates a local macOS draft producer-to-consumer
handoff. It still lacks an immutable producer release, Linux CI, actual
installed package byte mapping and an incoming upstream change trigger, so
R3 remains open.
