# Claim 003: getBlockDevices producer–consumer handoff

**Status: Proposed — not yet demonstrated in this ledger.**

## Claim to investigate

A freshly produced, identity-checked `getBlockDevices` source-observation table from a pinned ucode checkout is accepted by the pinned OpenWrt adapter when its source and policy prerequisites match. The consumer updates the intended retained effect in a disposable checkout while preserving unrelated rows; invalid inputs are rejected without writing those effect artifacts.

## Evidence to collect

1. First complete claim 002 on the selected producer revision. The producer table must be from the actual query run, not merely the committed CSV fixture; preserve command, output and source identities and diagnostics.
2. On a disposable consumer checkout at the chosen SHA, inspect the adapter's source-byte pin, corpus lock, exact row/columns, grant identities and independent mounts expectation. Choose a compatible producer/consumer pair; don't change the CSV or source by hand to make it pass.
3. Capture the relevant artifacts before importing. Invoke the actual adapter with the newly generated table and the matching source root. Verify its status, both target artifacts, expected record ID and location, grant associations, and preservation of unrelated rows. A valid table alone is not proof that the adapter ran.
4. In separate disposable copies, use a bad source digest and a malformed or wrong-identity row; record that each actual adapter invocation rejects and leaves both target artifacts unchanged. Record explicit initial state and output digests. If testing reimport, compare bytes after the first and second actual runs; do not call a current-state reimport a legacy migration.

## Boundaries

The adapter checks input and source bytes but cannot by itself authenticate that CSV was generated by CodeQL. This claim binds the observed local run by preserving actual producer and consumer commands and artifacts; it is not cryptographic attestation. The source table is not reachability, runtime execution, taint or an authorization violation. The consumer's intended-access assessment is tied to separate policy expectations, not derived from the table. No downstream scan is required.
